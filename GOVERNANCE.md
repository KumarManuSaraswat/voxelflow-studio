# Project governance

VoxelFlow Studio is an independent, open-source project in its incubation stage. It is currently maintained under a personal GitHub account. This document describes how the project operates now and how it can grow; it does not establish a company, foundation, or GitHub organization.

## Roles

**Contributors** improve code, examples, documentation, testing, and discussions. You do not need a formal role to participate.

**Maintainers** review contributions, decide scope, publish releases, and care for project security and community conduct. The initial maintainer and repository administrator is [@KumarManuSaraswat](https://github.com/KumarManuSaraswat). The current review owner is recorded in [CODEOWNERS](.github/CODEOWNERS).

Maintainer invitations are based on sustained useful contributions, sound review judgment, constructive collaboration, and willingness to take responsibility. Existing maintainers discuss nominations with the contributor, then record accepted appointments publicly and update this file and CODEOWNERS. Access should be limited to the responsibilities the person accepts. Maintainers may step down at any time and should arrange a handover where practical.

## Decisions

Discuss substantial changes through issues and pull requests, with the artist's workflow, compatibility, and maintenance cost made clear. Seek agreement and document the outcome. During incubation, the initial maintainer makes the final decision when agreement cannot be reached, explaining the reason publicly where possible.

Security incidents and personal conduct reports may require private discussion. Publish relevant outcomes without exposing credentials, exploitation details before a fix, or private personal information. Maintainers can take urgent action to protect users and document the change afterward.

## Releases and access

Maintainers publish versioned releases after relevant automated checks and documented manual verification. Beta status and untested environments must be explicit. A tag must match the package version; release notes describe user-visible changes and remaining limitations. Repository administration and release permissions are restricted to trusted maintainers.

## Growing into an organization

When there are additional active maintainers and a reason to share administration, propose a dedicated GitHub organization in a public issue. Agree on its name, owners, repository permissions, and continuity plan before transferring the project. Aim for at least two trusted owners once suitable maintainers are available, with strong account security and a documented recovery process.

A transfer should preserve the project history and MIT license, update installation and support links, verify plugin discovery, and announce the new home in the README and a release. Changes to governance should be proposed and reviewed publicly. Funding or sponsorship, if introduced later, needs separate transparent terms; no funding program or external affiliation is established by this document.
